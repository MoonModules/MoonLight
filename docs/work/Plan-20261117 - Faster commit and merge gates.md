# Plan: faster commit and merge gates

Plan of 2026-11-17, a Refactor, for the product owner's pick. **Goal: the fastest development cycle possible**, at every stage MoonWalk names: setting up a topic, developing on the host, on hardware (build, flash, verify), testing, committing, merging and releasing, and the CI feedback between a push and its result. The commit and merge gates cost more time than the change they guard: a round on 2026-11-17 ran the desktop build three times, the suite three times and the docs checks four times, each rerun after a one-line fix the agent could have avoided by writing the rule right the first time. The gates stay as strict as they are; what changes is when a rule is applied and how much a check reads.

## What exists

- **The trigger table** is machine-readable already: each gate in `moonwalk/13-document-commit.yaml` and `14-merge.yaml` carries its `given: changed:` globs and the script it runs. An agent reads it and types the gate chain by hand each round.
- **The checks read the whole tree**: `check_docgen`, `check_prose` (Vale) and `check_code` (lizard, jscpd) measure every file and compare totals with the committed counts, though a finding is listed per file already. `test_host.py` runs all 3,394 cases, `test_tooling.py --python` all 770.
- **Rough costs, measured on this laptop on 2026-11-17**: a desktop build after a widely included header changes, 5 to 8 minutes; the desktop suite, about 3 minutes; the Python tests, 1.5 to 2.5 minutes; `collect_kpi`, 1 to 2 minutes; an ESP32 build, several minutes; docgen, prose and check_code, under a minute each; the JS tests, 5 seconds.
- **Rules are applied after the fact**: an agent writes, the checks find a help line over its cap, a hard wrap, a negation or a function over the complexity limit, and the agent fixes and reruns. On 2026-11-17 that loop alone cost four docgen runs on one file.
- **Step 1 of the host plan, the same day, showed where a round's time goes**: a rename's two compile errors (a header declaration and a test helper) surfaced one full rebuild each, 5 to 8 minutes apiece, since the renamed headers are widely included; a BSD `sed -i -E` backup file (`ReceiverList.h-E`) was staged as the rename target and only the Reviewer found it; Network Send's help passed its 250-word cap after one added sentence, found by docgen four runs later; and the ESP32 build and the Python tests run side by side slowed each other on the laptop's cores.
- **Lessons of the host rename's rounds, the same day**:
  - **A check reads only tracked files**: files moved with `mv` are invisible to docgen, prose and check_code until staged, so their counts read low before staging and jump after; the runner reports untracked files under its globs rather than measuring without them.
  - **A rename carries its lines' old findings**: a line changed only by a substitution counts as added, so an old `today` or negation on it fails the gate; the hook (step 3) rewords such a line as the rename touches it.
  - **A gate builds what it measures**: `build_desktop.py --tests` links only the test binaries, so the app binary looked stale after it; the runner builds the targets each gate reads.
  - **The agent edits nothing in a change the product owner is staging**: a measurement that trimmed a test file in place was staged trimmed; a measurement works on a copy.
  - **A gate run starts once the change is complete**: every open decision (a list of identifiers for the product owner, a batch still reporting) is answered first, since a gate started while the change still moves runs again for the part that moved; step 6 of the host rename stopped one run midway for this. An agent's repo-wide command runs under `nice` too: three `git grep` runs with a heavy pattern took every core, raised the load to 77 and stalled the laptop's MoonLight encode worker.
  - **The Reviewer runs beside the first gate run**: it uses no local core, so the gates run while it reads; its fixes and the run's findings then go in one batch and one rerun, which the cache keeps to the gates whose inputs moved (the 2026-11-17 commit round, below). A batch touching every area reruns every gate once.
  - **A local gate compares with the base CI uses**: `check_prose` diffs against the local `main`, which lagged `origin/main`, so a dated word passed locally and failed in CI; the runner reads `origin/main` after a fetch.
  - **CodeRabbit reviews at most 100 files at once and a few pushes an hour**: a push of four commits went unreviewed on its rate limit, and the full review it was then asked for refused the branch's 371 files; each push stays under 100 files and spaced past the rate, or the outside review drops out without a failing check.
  - **A plan's verify step reads CI**: the Android, ESP32 and Teensy builds CI runs on every push are read from the pull request, not rebuilt locally, as step 6 does for the merge gate.
- **CI runs every build and test** on each push (macOS, Windows, Linux, Android, Teensy, the sanitizers, JS, Python, Vale), and the merge gate reruns much of it locally.
- **The gate runner** the Project's card "A gate runner that runs each commit check once, on its own inputs" described is this plan's step 2; the card is removed, so the topic has this one home.

## After-action review: the first commit round through the runner (2026-11-17)

**Intended**: one gate run beside the Reviewer, the Reviewer's and the run's findings fixed in one batch, one narrow rerun, commit. **Happened**: two full runs (418 s, 471 s) and a third needed, with the work around them done by hand as well. The records are `build/gates/run-20261117-225040.json` and `run-20261117-231838.json`.

**What ran twice, and why**

- **The whole gate set**: the rerun repeated all 16 gates, since the batch of fixes (twenty review findings and the first run's) touched C++, JavaScript, Python, the docs and the YAML, and the cache reruns a gate whose inputs moved. The cache pays off when fixes are narrow; a broad batch reruns everything once, which is still once rather than per fix.
- **The checks, by hand and in the runner**: before the first run the agent ran the full docgen, code and prose checks by hand to see where things stood (docgen three times, code three, prose six), each rewriting the committed counts, which the agent then restored. A look at the findings is `run_gates.py --only` or a check's `--files`, recorded and cached, not a full run.
- **A third run, for findings the write-time hook would have caught**: five docgen errors reached the rerun because the agent made those edits with shell scripts, and the hook fires on the Edit and Write tools only.
- **The S3 firmware**: rebuilt once mid-round and stale again by the rerun, since C++ fixes followed it; the commit process rebuilds a stale firmware without asking, so the runner does it once, after the last C++ change.
- **The KPI**, the slowest gate (168 s, 176 s), ran in full both times; the first run's tick (10 to 12 µs) was noise from gates beside it, the quiet rerun measured 7 µs.
- **The Reviewer** started twice, the first stopped by the Fable usage limit; the Opus fallback finished in 10 minutes.
- **help.json, by hand twice**: once after the second run found it stale, then again after the third run, since a guide shortened after the first regeneration left it stale once more. Docgen reads the committed help.json for the word caps, so one stale file failed it twice (stale, and a guide over 40 words that the source no longer had).
- **The host build, inside check_code**: the third run's code gate took 466 s, where the second run's took 63 s. Its incremental build (`cmake --build build/macos`, 4 jobs, for the compiler's hot-path warnings) recompiled 202 of 498 objects after one-line comment edits in widely included headers (Scheduler.h, Drivers.h, SystemModule.h); build-host then found the tree current (3.9 s). One build, then, but under a quick check's label, so the runner scheduled it as one, and the comment edits cost a third of the tree. ccache stood at its 5.0 GiB cap with 1,628 cleanups and a 40 % hit rate, the host, the tests and every ESP32 target sharing it; a comment-only change hits in its preprocessed mode only while the entry survives, so the cap evicting them is the hypothesis to measure.
- **The KPI on a comment edit**: its cache is keyed on the diff, so a guide shortened in a header reruns its 3 minutes, though the binaries it measures barely change.

**What took long, and how it gets quicker** (the rerun's gates; its 471 s is the sequential lane's sum, so that lane is the critical path)

| Gate | Time | Quicker |
|--|--|--|
| KPI | 176 s | Find what it spends: the tick matrix runs the app again after the scenarios already ran it; one run measured twice is the textbook move |
| Python suite | 95 s | Starts at once, beside the C++ lane, and shards with pytest-xdist: about 30 s off the critical path entirely |
| Scenarios | 72 s | Beside the host suite rather than after it; both read the same test build |

With step 15's scheduling the critical path becomes the test build, then the longest of the suite, the scenarios and the Python shards, then the KPI alone: about 260 s for a tree like this one.

**Sustained**: the Reviewer found two real defects (a retry that re-initialized every driver, a hook that could unstage the product owner's files); a progress line per gate and per minute kept the product owner informed; the Reviewer beside the gates cost no local core.

**Actions**, each a step below: step 15 (scheduling by need); step 16 (the write-time hook on every file change); step 17 (the runner rebuilds a stale firmware, then checks it); step 18 (the KPI measures what the scenarios ran instead of running it again); step 19 (docgen's help freshness cached by its inputs); step 20 (a proposal that names a bypassed hook rather than asking for a check the hook already makes); step 21 (help.json generated once, just before the commit); step 22 (check_code reads build-host's build); step 23 (the KPI cached by the binaries it measures); step 24 (ccache sized for every target). Steps 21 to 24 are tuned before the next commit's gate run. The lesson on the Reviewer below changes with this round's evidence.

- **Correction, 20:17 to about 20:35**: the five findings fixed with a test each, and every rise cleared by Extract Function; the code check ran three times by hand (2.5 min each) and jscpd once to find the clones, since check_code `--files` does not show duplicates.
- **Run 2, 20:34 to 20:48 (13 min 11 s)**: 15 of 16 passed, the help regenerated first; the firmware build alone took the first 5.5 minutes, every other gate waiting behind it, then the code check 214 s. The unit suite failed two MQTT cases that pass alone and as `test_host.py` runs them; it ran beside the scenarios and the docs gates, and a port collision in its log shows two processes contending: a flake of the parallel schedule. Its rerun alone passed in 31 s. The round: two full runs and one single-gate rerun, about 27 minutes of gates and 18 of correction between them.

**What went wrong: correction afterwards instead of prevention beforehand.**

1. **The write-time hook had not run all day.** `build/hook/checked.json` last changed at 08:35, as in the fourth round; the fourth review named the cause (a session continued from a summary loses the watcher) and nothing re-armed it. Every rise run 1 found, the complex and long functions, the large file, the British spelling, is a rule the hook reports per file in seconds.
2. **Most edits bypassed the hook's trigger anyway.** The agent edited through Python and `sed` in the shell rather than the Edit tool, and a `FileChanged` watcher only sees what it is told to watch; the same edits through the editor tools would still have needed the watcher alive.
3. **Duplication is visible only to a whole-tree run.** Four clones came from this change (two in the look's header code, HLS's even rule made identical to RTSP's, a test's setup copied); no per-file check reports them, so the first sign was the 13-minute gate.
4. **The Reviewer read the push only at commit time.** The look push was a plan step finished at about 19:15; its crash path and the picker regression waited an hour for the commit's Reviewer. The step loop the textbook table names (the Reviewer per finished step) did not run.
5. **Checks run by hand are not cached.** The agent ran the unit suite, the JS and Python suites, docgen and prose many times outside the runner during the day, and the runner ran them all again, its cache knowing none of them.

**Improvements, in the order they pay back:**

- **The hook proves it is alive, and the gate runs it first** (step 20's purpose, the textbook table's "per-file checks at commit" row): `run_gates.py` runs `hook_written.check()` over every changed file as its first gate, before any build, failing in seconds on what run 1 found after 13 minutes; and the agent checks `build/hook/checked.json`'s age at the start of a session and after a summary, re-arming the watcher when it is stale.
- **Edits go through the editor tools**, so a write-time check sees them; a shell edit is for a mechanical rename across files, followed by the hook's check on the files it touched.
- **Clones per change**: jscpd run over the changed files against the tree (check_code's own `clones()`, filtered to the diff) inside that first gate, so a copied block shows before the build; about a minute where the whole check costs 2.5.
- **The Reviewer at every finished plan step**, on that step's diff, as the step loop says; the commit's Reviewer then reads a diff already read.
- **The agent runs a check through the runner** (`run_gates.py --only <gate>`), never by hand, so every pass is cached and the commit run repeats nothing.
- **The code check split in two**: lizard, jscpd and the boundary rules report in seconds without a build; only the blocking-call and stack-frame rules wait for check_nonblocking's build.
- **The firmware build with ccache** (`CCACHE_ENABLE=False` today): the long pole of every round, mostly recompiling what did not change.
- **No gate waits behind the firmware build that does not need it**: in run 2 every gate waited 5.5 minutes for it, since it holds every core token; the cheap checks start first (step 15's own next).
- **A gate that shares a port or a folder with another runs after it, never beside it**: the unit suite and the scenarios each declare what they hold, as a `needs` or a resource the scheduler keeps exclusive.

## The plan against the textbook (2026-11-19)

The textbook shape is layered, each layer catching its class of defect at its cheapest moment: **shift left and fail fast** (Humble and Farley's commit stage: [under five minutes, never ten](https://www.oreilly.com/library/view/continuous-delivery-reliable/9780321670250/ch07.xhtml)), an **inner loop** of seconds on the file written and an **outer loop** of CI on the whole tree, every stage checking **only what changed** ([pre-commit](https://pre-commit.com/) on the staged files, [Nx affected](https://nx.dev/docs/features/ci-features/affected)), fed by **small batches** ([Google: about 100 lines a change](https://google.github.io/eng-practices/review/developer/small-cls.html); [DORA](https://dora.dev/guides/dora-metrics-four-keys/)). Agentic development adds that the agent needs a verification signal at every step ([Anthropic's best practices](https://code.claude.com/docs/en/best-practices)), that a guardrail must prove it is alive, since an agent cannot notice a missing check, and that the agent's memory and rule changes stay visible to the human.

| Layer | When | What runs | Catches |
|--|--|--|--|
| Inner loop | every edit, seconds | the per-file checks on the file written (docgen, code, prose, compile) | budgets, complexity, wording, as written |
| Step loop | per finished plan step, minutes | the affected tests, and the Reviewer on that step's diff | design and logic defects while the step is fresh |
| Commit stage | once, under ten minutes | the per-file checks over the whole diff first, then the affected builds and tests | what slipped, in seconds rather than minutes |
| Outer loop | merge, on CI | everything, whole tree | cross-cutting and platform breakage |

| Practice | Textbook | MoonLight has | Gap | Refinement, and what it removes |
|--|--|--|--|--|
| Per-file checks at commit | pre-commit and [lefthook](https://lefthook.dev/usage/commands/run) run their hooks on the staged files | `hook_written.py` at write time; the gate runs whole-tree checks | the gate trusts the hook ran; on 2026-11-19 it had not | `run_gates.py` runs the hook's `check()` over every changed file as its first gate, before any build; removes step 20's bypass proposal and the by-hand hook runs |
| A guardrail that proves it is alive | a [dead man's switch](https://healthchecks.io/docs/monitoring_cron_jobs/): alert when the heartbeat stops | the hook writes `build/hook/checked.json` | nothing reads it, so a silent watcher reads as a clean tree | the runner's first line: "hook last ran at <time>; N of M changed files unchecked" |
| Editor-time feedback | on-save checks; Claude Code's [FileChanged](https://code.claude.com/docs/en/hooks) fires whatever wrote the file | step 16 | whether a resumed session re-registers the watcher is untraced | trace it once (`claude --debug hooks` on a resumed session); the first row holds either way |
| Ratchet per file and rule | [Spotless `ratchetFrom`](https://github.com/diffplug/spotless/blob/main/plugin-gradle/README.md), [Betterer](https://phenomnomnominal.github.io/betterer/docs/introduction), [Notion's per-file counts](https://www.notion.com/blog/how-we-evolved-our-code-notions-ratcheting-system-using-custom-eslint-rules) | totals per rule in `code.json` and `docgen.json` | a rise written at 10:00 shows at 13:00 as a whole-tree total | step 4's open half: counts per file and rule, the gate checks each changed file's row, the total a sum; removes the whole-tree lizard and docgen runs per commit |
| Cheap checks first | the commit stage's compile, unit tests and analysis in minutes | longest-path scheduling; step 15's cheap-first open | every failure of four rounds came from docgen, check_code or the docs build, 6 to 8 minutes in | the per-file gate above is the fail-fast stage; removes the open part of step 15 |
| Review of a small change, early | Google reviews one self-contained change and measures [response time](https://google.github.io/eng-practices/review/reviewer/speed.html) | step 8: the Reviewer per finished step | on 2026-11-19 it read the whole day at the end | step 11's reviewed ref, and `--list` printing the unreviewed diff's size |
| Small batches | DORA; the repo's own 400 lines and ten files for a contribution (`14-merge.yaml`) | one combined commit per cycle, the product owner's call | evidence: the rounds took 30, 38, over 60 and 110 minutes | none proposed; the numbers are for the product owner to weigh |
| Test isolation | [pytest-randomly](https://adamj.eu/tech/2018/01/08/pytest-randomly-history/): a leaky test rarely survives a shuffled order | `test_main.cpp` resets each process-wide state by hand | each new static needs its reset; the missing one surfaced in a commit round | CI's sanitizer lane runs doctest `--order-by=rand` and prints the seed |
| Measure the gates | DORA's lead time, change fail rate, rework | step 1: a record per run | no number per round | a round record: lead time, runs per round, time to first failure, fail rate per gate, hook coverage; removes the hand-timed reviews above |

**The five refinements with the most saving per effort**, from the research: (1) the hook's checks as the runner's first gate over the diff, an hour; (2) the heartbeat line, minutes; (3) counts per file and rule, a day; (4) the round record, half a day; (5) random test order in CI's sanitizer lane, minutes.

## End states

| | End state | Gains | Loses |
|---|---|---|---|
| A | **The gate runner only**: the card as written. | Each gate runs once per round, a rerun only where its inputs changed. | Every check still reads the whole tree, and the rules are still met after the fact. |
| **B** | **Rules at write time, checks per changed file, CI as the full sweep**: the steps below. | Most findings never happen; a commit round costs the changed files' checks and the affected tests; the merge gate reads CI instead of repeating it. | A per-file mode in three checks and a test map to maintain. |

**Recommended: B.**

## Every script, its cost and its value

Measured on 2026-11-17: the PR runs of #255 and `hub75-encoder` and the main push that merged #254. GitHub Actions is free on a public repository, so a CI job costs wall time and attention, never money; a PR's CI finishes when ThreadSanitizer does, 6 to 8 minutes. Local figures are this plan's measurements; "est." marks an estimate from what the script runs. ### The largest savings, ranked

1. **Reruns after a rule fix, 15 to 25 min per commit round.** The 2026-11-17 round ran the build three times and the suite three times. The hook at write time (step 3) and the cached runner (step 2) cut each to one run.
2. **The merge gate reads CI, 12 to 20 min per merge.** Build, suite, Python, JS, docgen and the text half of `check_code` ran on the PR already; what stays local is the ESP32 freshness, the KPI, the bench and the judgment gates.
3. **One ESP32 build per branch, 5 to 9 min per commit.** `check_esp32_built` rebuilds the S3 after nearly any `src/**` edit; a CI S3 build on pull requests and a local build at the merge keep the guard at one build per branch plus platform changes.
4. **Affected tests, 3 to 4 min per commit.** The suite's affected cases instead of 3,403, and the Python tests that import the changed script instead of 770.
5. **KPI per merge and one suite run, 1 to 2 min per commit.** `collect_kpi` moves to the merge gate and stops running `mm_tests`; the scenario suite it carries moves into `host-tests`.
6. **Two CI changes with no wall saving:** `prose.yml` goes (fully covered by `findings.yml`), and CodeQL runs on main and weekly only (7 runner min per branch push).

## Open questions

- **How far "affected tests" may go before a full run**: every commit round runs the affected cases only, or the full suite once per round as now and the affected cases on a rerun. **Recommended**: affected only per commit, full at the merge gate and in CI, since CI runs the full suite on every push already.
- **Whether a hook may block**: the hook reports, or refuses the edit until its findings are fixed. **Recommended**: reports; a half-written change legitimately fails a check for a minute.
