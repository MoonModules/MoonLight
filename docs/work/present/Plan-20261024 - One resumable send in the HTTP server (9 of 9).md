# Plan: one resumable send in the HTTP server

Plan of 2026-10-24, a Restructure, from the Reviewer's general review of `HttpServerModule` (3,175 lines) on the branch that made a late state document, large controls and low-RAM sends resumable. The server serves a classic ESP32 with 40 to 66 KB of internal RAM free, ESP32-C3 bulbs, an S3 driving thousands of LEDs on the same task, a P4 on Ethernet, the Teensy and the desktops, and it is tuned for the S3 with PSRAM and one browser.

- **Half resumable, half blocking.** Embedded files, the state stream, the preview and a late `/api/state` body resume across ticks; patches, every REST answer written through a socket sink, flash-file downloads and firmware uploads still block the render loop on the client: a patch to a client that stopped reading freezes the LEDs up to 2 s before the close, a GET `/api/state` on a large S3 tree waits on each ACK, and a firmware upload without MoonBase freezes rendering up to 3 minutes.
- **Five mechanisms move bytes to a socket**, each with its own slots, budget, stall guard and low-RAM policy: the preview drain, the state stream, the transfer slots (upload, download, document), the embedded sends, and the blocking firmware pull. Three WebSocket header writers.
- **Every other bodied route still answers 400 to a late body on hardware.** The body waits are iteration counts of `delayMs(1)`, which a 100 Hz FreeRTOS tick rounds to a yield: 50 ms on the desktop, microseconds on the ESP32. `/api/control`, `/api/modules`, the list, WLED and firmware-URL routes fail when a client sends headers and body apart.

The goal: every send and every request body resumes across ticks through one mechanism, no client can stall the render loop, and the server's sizes follow from the boards and the clients it serves.

## What exists

- `FileTransfer` slots (upload, download, document) with `driveTransfers`, a 3 ms budget and a 10 s stall guard; `EmbeddedSend` slots; `StateStream` per control client with a `TreeCursor` that resumes inside a control; `PreviewSend` with a per-client cursor.
- The low-RAM lease (`maySend`, `endSend`, `sent`): below `kSendHeadroom` one send queues at a time, a stalled holder hands it on. Files, streams and the preview take it; patches, REST answers and downloads do not.
- `uploadPull` drains a firmware body under `kFirmwareIdleMs` and `kFirmwareUploadHardMs`.

## Steps

1. ✅ **One rule for every bodied request.** A body not all in yet waits in a Document slot, with the route's handler deferred until it is whole, as `/api/state`'s does; both iteration-count waits go. Unit tests: a state document and a control set sent after their headers apply and answer 200, with the tick unblocked meanwhile.
2. ✅ **One resumable send.** One `Send` slot, a connection plus a source (a flash span, a file read stream, a tree cursor with its fragment, a borrowed preview frame with its WebSocket header) and an offset, drained by one loop with one budget, one stall guard and the lease. The four drains, their slot tables and `sendWsTextFrame` go; a patch is a one-fragment stream; a REST state answer is a cursor; every download takes a slot. Unit tests: a client that stops reading never holds a tick past the budget and is reaped by the stall guard; each source arrives whole.
3. ✅ **Firmware as a push writer.** `platform::otaWrite(handle, bytes)` in place of the pull callback makes a firmware upload an Upload leg; `UploadSource`, `uploadPull` and both firmware timeouts go, and with them the render freeze. Verified on a board without MoonBase.
4. ✅ **Sizes from what the device serves.** One fact, at most two browsers at once, sizes the rest: the embedded-file slots from what two browsers fetch in parallel; the control and preview caps stay at eight and four, since quick refreshes fill four with connections not yet reaped and refuse the page, for about 0.6 KB; the state fragment scales with the largest free block as the drain chunk does; `FileTransfer::path` lives in the slot's own buffer; the leaf baseline walks once. A document is never refused because downloads hold the slots, and a slow body meets a minimum rate per stall window rather than a byte every few seconds.
5. ✅ **The desktop's UI folder in the platform layer.** `serveFile` probes `src/ui/` before the embedded copy on every device; the desktop substitutes its disk files into the embedded table and core keeps one path.
6. ✅ **`/api/types` without building every module.** It constructs, defines and releases every registered type per request. Measured on a classic first; if it matters, a build-time table of defaults.
7. ✅ **A control client's partial frame is its own.** One carry buffer serves eight clients, so two clients split in the same tick lose a frame: a per-client carry, or a close with status 1002 on an unparseable read (RFC 6455 section 7.1.7) so the client reconnects clean.
8. ✅ **Split the file by concern**, one class over three translation units: the server (parse, route, responses, sends), the state wire (subscriptions, cursor, stream, diff, patch), and the WLED shim. Then measure on a classic (MM-Olimex), an S3 with a large show (the StadBeest legs), a P4 and the desktop: tick time with a page load and with a client that stops reading.
9. ✅ **The state push spread over frames, and told what changed.** Each second the push walks every value a client views on the render task, in one frame: measured on `MM-Olimex` (314 values), about 16 ms with one card viewed and 45 ms with everything, where a frame takes 2.6 ms, so one frame a second runs 6 to 17 times long. The cached hash is found by a linear scan, quadratic in the values. A control write the system already sees (the API, the UI, `setControl`) marks its module changed, as `notifyValuesChanged` does for the Control card; a status rides the walk, at most a second late, since `setStatus` may run on the encode task where the early-patch list has no lock. What modules change by themselves (telemetry, displays, a module writing its own variable) is walked by a cursor a slice per frame, as the state stream sends, matching the cache by position rather than by search. Measured on `MM-Olimex` with a client viewing everything: the slowest frame of the second rose from 196 to 251–285 fps. The StadBeest legs vary by ±30 fps between runs while their show plays, too much to tell before from after.

## What it removes

Four of the five drains with their slot tables, budgets and stall guards; `UploadSource`, `uploadPull`, `kFirmwareIdleMs`, `kFirmwareUploadHardMs`; `sendWsTextFrame`; the two iteration-count body waits; the once-a-second walk of every viewed value in one frame; the desktop path probe in core; per-module construction on `/api/types`; about 1.3 KB of control-client slots. It adds one send slot type and one drain.
