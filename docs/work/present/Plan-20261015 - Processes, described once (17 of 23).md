# Plan: processes, described once

Plan, approved 2026-10-15. MoonLight has many processes, from a first reader to a release, and each was written in its own place and shape. This plan finds one model for all of them, so a process is described once and followed by everyone it concerns: a user in the app, a reader of the docs, a test, an AI agent and the product owner. It is called **MoonWalk**: the model, its stage files under `moonwalk/`, and the map that shows them.

Where things are described: [the MoonWalk reference](../../reference/moonwalk.md) is what exists and how to use and write it; [the model](../future/moonwalk.md) and [its schema](../../../moonwalk/moonwalk.schema.json) are why it is shaped so, chosen against the textbooks (Patton's story map, Arazzo, Given-When-Then, Diátaxis); [the inventory](../future/processes-inventory.md) lists the 71 processes found. This plan holds what is still to build, and a line per step done.

## Why

The same steps lived in several places: installing on the desktop was a how-to, a getting-started section, a README paragraph ; the commit gates a diagram and prose in CLAUDE.md, the scripts in MoonDeck.md and the agents' memory; a scenario listed steps in its own format. Every copy drifted on its own. **What it removes**: the duplicated step lists, the separate step formats once the mapping shows which reduce to one, the hand-written gate results in commit messages once the gates record on GitHub, and `collect_kpi.py`'s own map of which script measures what, once each step declares its metrics.

Neither a Confluence nor a Jira: the docs site is ours and GitHub's issues and Projects track work. What is built is a schema, the process files, one generator and an adapter in each runner. Out of scope: a process engine, an editor, a server, states or permissions beyond GitHub's. The map and its renderer download within 50 KB; the firmware carries none of it.

## Still to design

**The runners.** A runner performs the steps it knows and skips or describes the rest. Built: the app (Show me, the follow bar), MoonDeck (Run, the gates), the docs (the map and the site). To build: the scenario runner and the unit tests as runners of a process's steps (step 17), and agents reading a process for the task they are given.

**The APIs a step calls.** Built: the device's REST API in OpenAPI 3.1. Candidates: the WebSocket's state stream, as AsyncAPI, once a process needs to wait on a pushed state; the GitHub REST and GraphQL APIs for releases, issues, check runs and Projects; MQTT and Home Assistant as tool steps. Two tools are worth a look once they replace code of ours: Redocly's Respect runs Arazzo workflows against an API, and Spectral lints them.

**Flows.** Built: `dependsOn` orders processes, a `process` step runs another, and a choice (`inputs`, `given`) is a branch. Not built: a Mermaid flowchart per process with a lane per actor, which CLAUDE.md's diagrams were to become. BPMN is the move only if a process needs timers, events or swimlanes, which none does.

**Metrics on steps.** A step declares what it measures, as Arazzo declares a step's `outputs`, and each run records the values on its instance, so a process carries its measurements rather than a report knowing which script produces which number. The measurements exist, spread over scripts: a scenario's tick time and heap, a build's flash size, the code ratchets, the gate times. `collect_kpi.py` gathers them per commit; the process file would name them per step, and the trend of a value is the series of its runs. The process itself is measured the same way: the DORA metrics (lead time, deployment frequency, change failure rate, time to restore), with a control chart to tell noise from a shift.

**Across origins and MoonCloud.** Browser storage stays on its origin, so what crosses origins is carried. Built: the address (`?walked=install`, the installer's handover). Candidates: `postMessage` between a page and a window it opens; marks kept on the device's own config, which costs a persisted control the 2026-10-16 decision kept out; and MoonCloud, with consent. A MoonWalk member of MoonCloud, its own checkbox and off until switched on like Stats and Talk, keeps the marks under the installation id so they follow the device to every browser, and in aggregate shows where people stop, a funnel per process. It sends process and step ids and nothing typed, under the privacy policy's rules (step 22). One consent already covers what the app reads from the docs site, the help and MoonWalk (decided 2026-10-16).

**GitHub: issues, Projects, CI, the backlog and notes.** MoonWalk in the repo is the definition; GitHub holds the work and the runs, each feature one job. **Issues** are the work items, each labelled `walk:<process-id>` so the map shows open issues per process, and the issue forms are generated from MoonWalk (the steps of Log an issue become the bug form). **The backlog becomes the Project's draft items**: four Markdown files of 4,051 lines beside 4 open issues are two backlogs for one job (step 21). A draft item becomes an issue when it is accepted, so the issue list holds only accepted work and reports. **A Project** orders them: Status (Inbox, Backlog, Next, In progress, Waiting, In review, Done), Waiting holding work blocked on someone outside the project: a reply, a part, a tester, a Stage and a Process field, an Area. **Notes reach the Inbox** as a Project draft item, from the phone, `gh project item-create` or the agent, triaged into an issue or deleted (step 20). **Actions run what is already executable**: a step names a workflow, the local gates post check runs (step 19). Access: the agents' `gh` needs the `project` scope.

19. 🚧 **Executions on GitHub.** (Built 2026-10-25: `CONTRIBUTING.md`; the pull request template, generated from the questions `contribute-pr`'s steps ask in their new `asks` field; the pull request workflows as thin callers of the scripts `ci-on-pr` names, held so by `test_workflows.py`. Missing: `release.yml`'s build steps, after v7.0.0 ships; ThreadSanitizer locally in a Linux container; recorded runs and their state.) A process file is the definition and one run of it is an instance, the split workflow engines make. GitHub keeps the instances; the definition stays in the repo as the one copy. **Decided 2026-10-25:** `CONTRIBUTING.md` is written by hand as one sentence linking [Contribute a pull request](../../moonwalk.md#contribute-pr), since a link copies nothing and needs no generator. `.github/pull_request_template.md` is generated from `contribute-pr`: it asks what the process says a pull request states (one topic within the size cap, based on main, what an agent wrote, what was tested) and links the steps, without a checklist of them. Steps come in two kinds:
    - **Volatile steps** act on a device or in the app, such as a user choosing an effect. Nothing records them, since nothing outside the device changes.
    - **Recorded steps** change the repo or what ships: a plan step, a commit gate, a merge, a release, a verification on hardware, a gallery submission. Each run leaves a record.

    A run's state is Started, Done or Stuck. Stuck is a run waiting at a prompt for minutes, which `walk_status` reports as it reports a stale gate, and which reaches the product owner where they read, Discord included. Seen 2026-10-21 in a community member's setup: a bot posting each agent run's Started, Done and Stuck to Discord.

    A run's measurements, the step metrics above, ride on its record: a check run's output on GitHub, and the value series repo-health draws.

    Automated recorded steps record as check runs on the commit or pull request, the local gates included through `gh api`, so a pull request shows which gate passed on which commit. Manual recorded steps record in an issue created from an issue form generated from the process file, a step per sub-issue, and a GitHub Project shows every run and the step it stands at. **Decided 2026-10-25:** a step's kind follows from its process, not its action, since `manual` and `run` go both ways ("Test it on real hardware" in Release is recorded, "Adjust its controls" in first-light-show is not). Every step of a gate process MoonDeck lists, plus `pick-spec-plan` and `contribute-pr`, is recorded; every other step is volatile. A per-step override waits for a step that needs one. Still to decide: whether a plan becomes such an issue instead of a file in `docs/work/present/`, which changes CLAUDE.md's process. **Recommended (2026-10-25):** a plan stays a file, reviewed in a diff and kept in git; revisit once step 20's trial of the Project has run.

    **Every CI job also runs locally**, so a GitHub outage, or a CI service that changes or stops, costs a runner rather than the gates. A workflow is a thin caller of the MoonDeck script its process step names, and GitHub is one runner of the process files among others. Today each job reproduces by its own script, as `ci-on-pr` lists them, but not as one command, and four gaps remain: ThreadSanitizer needs Linux (`check_sanitizers` skips it on macOS), the MSVC build needs Windows, CodeQL needs its command-line tool, and the release's publishing (the release upload, Pages, the container registry) is GitHub's. The work: one MoonDeck entry runs `ci-on-pr` and `release`'s build steps locally, through `walk_status` as the commit checks already run; ThreadSanitizer runs in a Linux container; every workflow line that is not a script call moves into one; and a test reads `.github/workflows/` and fails on a job that calls no script a process step names.

## Decided

- **One install process with a platform choice** over a process per platform (step 7): the steps they share are written once.
- **MoonBase links the map rather than hosting it** (step 6), since a board in recovery often runs offline.
- **MoonWalk decides and MoonDeck serves**, with no runner script of MoonWalk's own (step 9): a step names a script and MoonDeck runs it.
- **A process no runner verifies is listed, not counted** (step 15), since a count of them could never fall: they are the ones a person alone can judge.
- **A `call` gets no derived `then`** (step 16), since its result is not in its action; one is written by hand where the call changes the device.
- **`CONTRIBUTING.md` links, the pull request template is generated** (step 19): only what copies the process's content is generated.
- **A step's kind follows from its process** (step 19): a gate process records its runs, any other is volatile.
- **A step has no loop** (step 17), as Gherkin has none: a format with variables and repetition is a programming language. Work that repeats over boards or measures a spread stays a script a `run` step names.
- **`onSuccess` and `onFailure` left the schema**, 2026-10-20, as no process used them.
