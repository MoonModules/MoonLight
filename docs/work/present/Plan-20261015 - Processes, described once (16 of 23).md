# Plan: processes, described once

Plan, approved 2026-10-15. MoonLight has many processes, from a first reader to a release, and each was written in its own place and shape. This plan finds one model for all of them, so a process is described once and followed by everyone it concerns: a user in the app, a reader of the docs, a test, an AI agent and the product owner. It is called **MoonWalk**: the model, its stage files under `moonwalk/`, and the map that shows them.

Where things are described: [the MoonWalk reference](../../reference/moonwalk.md) is what exists and how to use and write it; [the model](../future/moonwalk.md) and [its schema](../../../moonwalk/moonwalk.schema.json) are why it is shaped so, chosen against the textbooks (Patton's story map, Arazzo, Given-When-Then, Diátaxis); [the inventory](../future/processes-inventory.md) lists the 71 processes found. This plan holds what is still to build, and a line per step done.

## Why

The same steps lived in several places: installing on the desktop was a how-to, a getting-started section, a README paragraph ; the commit gates a diagram and prose in CLAUDE.md, the scripts in MoonDeck.md and the agents' memory; a scenario listed steps in its own format. Every copy drifted on its own. **What it removes**: the duplicated step lists, the separate step formats once the mapping shows which reduce to one, the hand-written gate results in commit messages once the gates record on GitHub, and `collect_kpi.py`'s own map of which script measures what, once each step declares its metrics.

Neither a Confluence nor a Jira: the docs site is ours and GitHub's issues and Projects track work. What is built is a schema, the process files, one generator and an adapter in each runner. Out of scope: a process engine, an editor, a server, states or permissions beyond GitHub's. The map and its renderer download within 50 KB; the firmware carries none of it.

## Still to design

**The runners.** A runner performs the steps it knows and skips or describes the rest. Built: the app (Show me, the follow bar), MoonDeck (Run, the gates), the docs (the map and the site). To build: the scenario runner and the unit tests as runners of a process's steps (step 17), and agents reading a process for the task they are given.

**The APIs a step calls.** Built: the device's REST API in OpenAPI 3.1. Candidates: the WebSocket's state stream, as AsyncAPI, once a process needs to wait on a pushed state; the GitHub REST and GraphQL APIs for releases, issues, check runs and Projects; MQTT and Home Assistant as tool steps. Two tools are worth a look once they replace code of ours: Redocly's Respect runs Arazzo workflows against an API, and Spectral lints them.

**Flows.** Built: `dependsOn` orders processes, a `process` step runs another, and a choice (`inputs`, `given`) is a branch. The schema's `onSuccess` and `onFailure` were removed 2026-10-20 as unused. Not built: a Mermaid flowchart per process with a lane per actor, which CLAUDE.md's diagrams were to become. BPMN is the move only if a process needs timers, events or swimlanes, which none does.

**Metrics on steps.** A step declares what it measures, as Arazzo declares a step's `outputs`, and each run records the values on its instance, so a process carries its measurements rather than a report knowing which script produces which number. The measurements exist, spread over scripts: a scenario's tick time and heap, a build's flash size, the code ratchets, the gate times. `collect_kpi.py` gathers them per commit; the process file would name them per step, and the trend of a value is the series of its runs. The process itself is measured the same way: the DORA metrics (lead time, deployment frequency, change failure rate, time to restore), with a control chart to tell noise from a shift.

**Across origins and MoonCloud.** Browser storage stays on its origin, so what crosses origins is carried. Built: the address (`?walked=install`, the installer's handover). Candidates: `postMessage` between a page and a window it opens; marks kept on the device's own config, which costs a persisted control the 2026-10-16 decision kept out; and MoonCloud, with consent. A MoonWalk member of MoonCloud, its own checkbox and off until switched on like Stats and Talk, keeps the marks under the installation id so they follow the device to every browser, and in aggregate shows where people stop, a funnel per process. It sends process and step ids and nothing typed, under the privacy policy's rules (step 22). One consent already covers what the app reads from the docs site, the help and MoonWalk (decided 2026-10-16).

**GitHub: issues, Projects, CI, the backlog and notes.** MoonWalk in the repo is the definition; GitHub holds the work and the runs, each feature one job. **Issues** are the work items, each labelled `walk:<process-id>` so the map shows open issues per process, and the issue forms are generated from MoonWalk (the steps of Log an issue become the bug form). **The backlog becomes the Project's draft items**: four Markdown files of 4,051 lines beside 4 open issues are two backlogs for one job (step 21). A draft item becomes an issue when it is accepted, so the issue list holds only accepted work and reports. **A Project** orders them: Status (Inbox, Backlog, Next, In progress, Waiting, In review, Done), Waiting holding work blocked on someone outside the project: a reply, a part, a tester, a Stage and a Process field, an Area. **Notes reach the Inbox** as a Project draft item, from the phone, `gh project item-create` or the agent, triaged into an issue or deleted (step 20). **Actions run what is already executable**: a step names a workflow, the local gates post check runs (step 19). Access: the agents' `gh` needs the `project` scope.

15. ✅ **The checks.** Done 2026-10-20. A step that names a script, a scenario, a page with its anchor or an API operation that does not exist fails the build, as does a module or control `help.json` does not know. A process no runner verifies is reported: none of its steps has a test, CI or an agent that performs it, or a condition the device state answers, listed by `check_docgen` as information, not counted (14 processes today, the ones a person alone can judge), since a count of them could never fall. A check that could not run writes no report: `check_docgen` recorded a missing libclang as an error in `docgen.md`, which a contributor committed (#144); an unchecked result prints and leaves the report alone. [What it checks](../../reference/moonwalk.md#9-what-the-generator-checks).
16. ✅📖 **Steps that know they are done.** Done 2026-10-20. A step's `then` is what the device shows once the step holds; it lets the app mark a step done and offer the next, and is a test's assertion. The generator derives it for an `add` and a `set`, whose result is their action, so it has one home. A writing `call` carries none unless one is written by hand, since its result is not in its action: the six device-changing steps of `http-api`, `apply-state` and `moonlive-api` now carry one, but a script-declared control such as `hue` is not in `help.json`, so that step has none. The measure holds: every process that changes the device marks itself done. The pass over the 221 manual steps found one that names a concrete control and value (`control-surface/share`), now two `set` steps; the rest name a choice or a value the reader picks. 29 of 478 steps carry a `then`, in 13 processes. The map shows each condition under its step, and a done process names its reason ([how](../../reference/moonwalk.md#2-what-the-map-knows-by-host)).
17. 🚧 **Examples of a process: the tests.** (Missing: the loop vocabulary decision, so `run_network_live.py` and `run_network_roundtrip.py` stay scripts.) A process is the outline, a how-to with the reader's values left open. A scenario is an example of it, Gherkin's Scenario Outline and its Examples (specification by example): it fills in concrete values to prove behavior. What a scenario and a process share is small: the target keys, a module type and a control as `help.json` keys them, and the expectation shape, a scenario's `expect_control` converging on a process's `then`. The link is a key in the test naming the steps it proves, so the map shows a step tested and a renamed step fails the build. The pilot is `Layers_stack_and_blend_live`. The unit tests link the same way, so the process steps orchestrate the whole test system: a test, a scenario and a live run each name the step they prove, the link living in the test, and the map derives per step the tests that cover it, so a reader sees in MoonWalk that a process was tested. This step's check works both ways: a test naming no step that exists fails, and a step no test covers is reported. To decide: whether the step vocabulary learns a loop, so `run_network_live.py` and `run_network_roundtrip.py` become scenarios rather than scripts.
    - **The test index and the test engine** are [their own plan](../past/plans/Plan-20261020%20-%20Test%20engine%20(shipped).md): `tests.json` replaces the generated test pages and carries the cross-links this step needs, from tests to steps, modules and controls.
18. ⏳ **Guides that add, and `@technical` trimmed**, from the help plan. A control's `@guide` line says only what its line cannot hold, and a module with depth gets a guide about itself, how it works and how to get a look, rather than one walking its controls. An `@technical` appendix keeps only what neither the code, the test names, the base class nor the help says, one or two sentences each; a fact every module of a role shares is said once in the role's base class. Judgment work over hundreds of headers, read here for the processes it holds: a guide's "how to get a look" is a process's steps, so the inventory of step 1 reads the guides and appendices, and what is procedural moves into a process file rather than being trimmed twice. What is reference rather than reasoning, control tables, protocols and wire formats, moves to `reference/`, so it is the one folder for detail; why the code is built as it is stays at the code, where it changes with it, and the appendix line count falls rather than relocates.
19. ⏳ **Executions on GitHub.** A process file is the definition and one run of it is an instance, the split workflow engines make. GitHub keeps the instances; the definition stays in the repo as the one copy. To decide: whether a pull request template and a `CONTRIBUTING.md` are generated from `contribute-pr`, or README's Contributing section links the map. Steps come in two kinds:
    - **Volatile steps** act on a device or in the app, such as a user choosing an effect. Nothing records them, since nothing outside the device changes.
    - **Recorded steps** change the repo or what ships: a plan step, a commit gate, a merge, a release, a verification on hardware, a gallery submission. Each run leaves a record.

    A run's state is Started, Done or Stuck. Stuck is a run waiting at a prompt for minutes, which `walk_status` reports as it reports a stale gate, and which reaches the product owner where they read, Discord included. Seen 2026-10-21 in a community member's setup: a bot posting each agent run's Started, Done and Stuck to Discord.

    A run's measurements, the step metrics above, ride on its record: a check run's output on GitHub, and the value series repo-health draws.

    Automated recorded steps record as check runs on the commit or pull request, the local gates included through `gh api`, so a pull request shows which gate passed on which commit. Manual recorded steps record in an issue created from an issue form generated from the process file, a step per sub-issue, and a GitHub Project shows every run and the step it stands at. To decide: whether a step's kind is declared or follows from its action, and whether a plan becomes such an issue instead of a file in `docs/work/present/`, which changes CLAUDE.md's process.

    **Every CI job also runs locally**, so a GitHub outage, or a CI service that changes or stops, costs a runner rather than the gates. A workflow is a thin caller of the MoonDeck script its process step names, and GitHub is one runner of the process files among others. Today each job reproduces by its own script, as `ci-on-pr` lists them, but not as one command, and four gaps remain: ThreadSanitizer needs Linux (`check_sanitizers` skips it on macOS), the MSVC build needs Windows, CodeQL needs its command-line tool, and the release's publishing (the release upload, Pages, the container registry) is GitHub's. The work: one MoonDeck entry runs `ci-on-pr` and `release`'s build steps locally, through `walk_status` as the commit checks already run; ThreadSanitizer runs in a Linux container; every workflow line that is not a script call moves into one; and a test reads `.github/workflows/` and fails on a job that calls no script a process step names.
20. ⏳ **The Project and the inbox on GitHub.** The Project with its fields and views, the `walk:` labels, the issue forms generated from MoonWalk, and the map's count of open issues per process. Apple Notes stays the scrapbook it is, the quickest place for a thought. The Inbox is tried as the step after it: a note worth acting on moves there and is triaged. Whether the Inbox can be the scrapbook too is learned by using it, and Apple Notes goes only if it can. Independent of the other steps, so it can run whenever the product owner picks it. Before step 21, about ten backlog items are moved as draft items and used for a while: queried and edited with `gh`, one converted to an issue, the board mirrored to JSON. What does not hold up in daily use changes step 21 before the rest moves.

21. ⏳ **The backlog moves to the Project.** Decided 2026-10-21. Each backlog item becomes a **draft item** in the Project's Backlog column, not an issue: around 230 items as issues would bury the open issues, and a draft item stays out of the issue list while `gh` still queries and edits it. A draft item becomes an **issue** when the product owner moves it to Next, which is the acceptance and the point where an agent may pick it up. An **analysis** stays a file in `docs/work/future/`, which the item links, so the reasoning stays in git and is reviewed in a diff; an item whose text is longer than a card holds moves to such a file. A script **mirrors the board** to a JSON file, so an agent searches it offline as it searches the docs. A script reads the four backlog files, proposes one draft item per actionable item with its area and a link to any analysis it cites, and writes the list for the product owner to review before anything is created. Then it creates the items, and the four files are deleted in the same change. An item already shipped or no longer wanted is dropped in the review rather than migrated. After step 20 and its trial, since the items land in its Project.

22. ⏳ **MoonWalk in MoonCloud.** The member above: its card and consent text, a route and a table in the MoonCloud worker, the privacy policy's entry, and the funnel shown back on the card as Stats shows its totals. It follows step 4, since only the app has an installation id.

23. ⏳ **Close the plan.** Once 15 to 22 are done: the lessons the steps taught go to `docs/work/past/lessons.md`, `moonwalk.md` is read against the built system, and the plan moves to `docs/work/past` as shipped. Deleting it is the product owner's call.
